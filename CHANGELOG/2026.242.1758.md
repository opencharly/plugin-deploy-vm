# 2026.242.1758 — feat(vm): grant an iso guest passwordless sudo at prepare-venue

## Summary

A deploy onto an ISO-installed guest dies in its first package step:

```
sudo: a terminal is required to read the password; either use ssh's -t option
      or configure an askpass helper
sudo: a password is required
charly: error: ... walk step "SystemPackages" ... system packages pac: exit status 1
```

Every other VM source kind gives charly a rootfs it controls, and the passwordless sudoers
drop-in is written while building it — the distro entities' `bootloader.install_template`
does exactly that for a bootstrap VM. **An installer ISO does not**: the distro's own
installer creates the account.

## There is no declarative way to ask for it

Verified against the shipping Omarchy 4.0.1 ISO's own squashfs, not assumed:

| Candidate | Why it does not work |
|---|---|
| archinstall `"sudo": true` | `enable_sudo` writes `<user> ALL=(ALL) ALL` — **password required**, no NOPASSWD option in the schema |
| archinstall `custom_commands` | present in archinstall's own arg parser, but **Omarchy's orchestrator never reads it** — emitting it would have been another dead field |
| Omarchy orchestrator hook | it has no user/sudo phase at all; `configure_ssh_access` does keys, sshd and the firewall, nothing else |
| a NOPASSWD group to join via `"groups"` | `omarchy-settings` ships only **command-scoped** drop-ins (`asdcontrol`, `dns`, `tzupdate`) |

So charly finishes provisioning the guest it just installed, **using the credential it
authored for that install**. This is the same act as the bootstrap path's sudoers write,
moved to the only moment an ISO install allows it: `prepare-venue`, before
`EnsureCharlyInGuest` — the first thing that needs root.

## How the credential is handled

Every point below is asserted by a test that **fails when the guarantee is removed**:

- **Stdin, never argv.** A negative control replacing it with `echo <pw> | sudo -S` fails
  with *"the password appeared in the COMMAND on call 1 … visible in ps to every user on the
  host"*.
- **Idempotent.** A guest that can already sudo is probed and left alone, so a re-deploy
  sends nothing at all. That is also the whole function on a distro whose installer already
  granted it — charly does not assume it is the only thing that could have.
- **Verified.** Removing the re-probe fails the test: a drop-in that did not take effect must
  not be reported as success, or the next package step fails with the same opaque message.
- **Directed failure.** No password *and* no passwordless sudo is an error naming both ways
  out, never a silent skip.
- **`visudo -c` before install.** An unparseable file in `sudoers.d` locks the account out of
  sudo entirely — far worse than the state we started in.

Scoped to `source.kind: iso`. Every other kind never probes, never writes, never sends a
credential.

That is the before/after, on one guest, one seed, one bed.

### The two blockers the old text cited are both resolved

The previous revision said the live run was blocked behind two other defects. Both are closed,
and neither turned out to be what it was called:

- **The host-key pin** — `opencharly/plugin-vm#12`, **merged**. It was necessary but not
  sufficient: the stanza had a *second* writer in this very file, fixed in
  `opencharly/plugin-deploy-vm#7`, **merged**.
- **"The guest hangs in its initramfs"** — **there was no hang.** Root-caused to mkinitcpio's
  unconditional `encrypt` and `resume` hooks finding nothing to act on; both messages end with
  "continuing", the UKI cmdline carries no `cryptdevice=`, and the guest reaches a full
  multi-user system with sshd active. That characterisation was wrong and is withdrawn.

`airootfs.sfs` from the shipping ISO and reading its own loader, which searches both cases.
The run above is with that fix in place.

So the zero-warning gate is met by **removing the warning**, not by classifying it.

## Rulebook compliance

- **R1 — RCA every anomaly.** Four candidate declarative fixes were each checked against the
  ISO's own files and eliminated with evidence before writing any code.
- **R2 — Finish the whole cutover.** The helper and its call site ship together; there is no
  second path and nothing deferred.
- **R3 — No duplication.** One function owns the credential; `RemoteRunner` is injected so
  the password path exists in exactly one reviewable place.
- **R4 — No workarounds.** The rejected alternatives were: emitting a `custom_commands` block
  nothing reads, and weakening the bed to deploy nothing. Neither removes the defect.
- **R4a — Fix the product first.** The documented-caveat version of this ("your iso guest
  needs manual sudo setup") would have made the defect permanent by making it look intended.
- **R5 — Delete legacy completely.** N/A — additive; no path replaced.
- **R6 — Git safety.** `git status` inspected before the commit; no force-push, no direct
  push to `main`.
- **R7 — Prove behavior, not compilation.** Three negative controls, each shown to fail the
  guarantee it protects.
- **R8 — Preserve emitted artifacts.** The emitted artifact is the sudoers drop-in, and it is
  validated with `visudo -c` before installation and re-probed after.
- **R9 — Binary equals source.** N/A for this repo — plugin-deploy-vm is a candy, not a
  binary. It adds no runtime OS dependency: `sudo`, `visudo` and `install` are already
  required by any guest charly deploys to.
- **R10 — Fresh disposable proof.** Met. `check-omarchy-iso-vm` is `disposable: true` and
  reaches `PASS (steps=9)` **at zero non-allowlisted warnings** with this branch, and the
  changed function's own output
  (`granted user passwordless sudo (/etc/sudoers.d/99-charly-user)`) appears in that run's
  `deploy-add.log`, before `EnsureCharlyInGuest` as designed. The grant was then verified in
  the guest with `sudo -n`. Both blockers cited by the previous revision are closed:
  plugin-vm#12 is merged, and the "initramfs hang" was root-caused as non-fatal mkinitcpio
  hook output — there was no hang, and that characterisation is withdrawn.
