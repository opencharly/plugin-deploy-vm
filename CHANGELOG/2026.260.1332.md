# 2026.260.1332 — feat(readiness): probe the guest agent + domain state BEFORE the sshd wait

## Summary

The VM deploy's `prepare-venue` waited on sshd with a blind 30-minute cap. A
**crashed / shut-off / absent domain** therefore burned the entire cap and then failed with a
generic `absolute cap exceeded` — with no indication the domain was dead the whole time.

### RCA (R1)

Measured on `check-omarchy-eval-edge-inst`: `deploy-add` ran 30m55s and failed with

```
plugin-deploy-vm prepare-venue: wait-for-sshd: ... ssh-ready: poll: absolute cap exceeded (cap 30m0s)
```

while the domain had never booted. There was **no boot signal earlier than sshd** and **no way
to distinguish "still booting" from "will never be ready"**, so the poll could only exhaust its
cap.

### Fix — probe the guest agent + domain state FIRST

A new `(c0)` readiness gate runs **before** the SSH bootstrap, invoking the vm plugin's
`guest-ping` internal op (over the `verb:libvirt` `OpRun` reverse channel — the same path
plugin-preempt / plugin-ssh / plugin-substrate use), which checks the **domain state** and, only
if running, pings the **qemu-guest-agent** (which answers only once the guest OS is up — a real
boot signal, strictly stronger than sshd):

- a **TERMINAL** domain (crashed / shut off / absent / unreachable) → `ErrPollFatal`, so the poll
  **aborts on the FIRST probe** (a dead domain is detected in seconds, not after 30 minutes);
- a merely **booting** guest (domain running, agent not yet connected) → transient, keeps polling;
- a probe that **cannot be made** (vm plugin unconnectable / op absent / RPC error) → also
  `ErrPollFatal` with the cause, NOT masked as "still booting" (the masking the RCA names);
- only a READY agent proceeds to the sshd wait.

The gate is **data-driven**: skipped unless the VM entity declares the guest-agent channel
(structured `channels:`, or a raw `libvirt.snippets:` string) — this plugin serves every repo's
VM deploys, so an unconditional wait would deadlock a guest that has no agent.

**Dependency:** the op (`guest-ping`) ships in `opencharly/plugin-vm#35`. Per the B15 landing
order that op PR lands FIRST; this PR was then re-derive-validated against the op's merged
behaviour (the live run below serves the op compiled into the host binary).

### The live bed CAUGHT A REAL BUG (the value of running it)

The first live run failed — and correctly so:

```
[deploy-add] FAIL after 21.372s:
  wait-for-guest-agent: ... domain "charly-charly-check-guest-agent-vm" is absent — it cannot become ready
```

The gate had double-prefixed the domain name: `in.Alias` is **already** the libvirt domain
(`kit.VmSshAlias(domainID) == "charly-"+domainID`), so `"charly-"+in.Alias` looked up a
non-existent `charly-charly-<id>` and reported a RUNNING domain as absent. The terminal-abort
path worked (fast 21s fail, not a 30m cap — the fix's whole point), but the verdict was wrong.
The second commit fixes it; the PASS above is the post-fix run. This is exactly the class a
unit test cannot catch and a live bed does.

### SDD note (the `vmGuestAgentState` decode)

The gate's reply decode (`vmGuestAgentState`, `json.Unmarshal`) is a hand-written consumer
struct for the vm plugin's internal-op reply. The `guest-ping` **request** rides the CUE-sourced
`spec.VmPluginEnv` (the shared `#VmPluginEnv` def). Internal-op **replies** are decoded by field
name at every existing consumer — `plugin-preempt` (`var st struct{ Running bool }`),
`plugin-substrate`, `plugin-ssh` — because they are versioned with the serving plugin, not part
of the authored-config contract (`#VmResolveResult` is the one reply promoted to CUE, for the
graphics-endpoint path). This consumer follows that established shape; promoting it to CUE would
require a coordinated `spec` change landing before this PR and is not needed for a
plugin→plugin reply whose producer ships in the companion PR.
