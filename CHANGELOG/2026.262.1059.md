# 2026.262.1059 — fix(readiness): prepare-venue must not wait on the qemu-guest-agent

## Summary of changes

**RCA + fix: prepare-venue must not gate on the qemu-guest-agent.**

`vmPrepareVenue`'s (c0) readiness gate polled the guest agent (`guest-ping`) to readiness — reasoning that the agent is a stronger boot signal than sshd. True, but the agent is installed by a **candy applied LATER in the same deploy**: eval-omarchy's `omarchy-eval-record` runs `pacman -S qemu-guest-agent` during `deploy-add`, AFTER prepare-venue. On a fresh ISO install the agent is therefore absent for the entire prepare-venue phase, so the poll could not distinguish "OS still booting" from "agent never installed in this phase": it retried to the **30-minute absolute cap** and failed **every first provision**.

Measured live on `check-omarchy-eval-base-inst` (omarchy 4.0.4):

```
[deploy-add] FAIL after 30m27.588s: ... plugin-deploy-vm prepare-venue: wait-for-guest-agent:
  guest-agent: poll: absolute cap exceeded (cap 30m0s)
```

while `ssh` to the same guest worked the whole time.

**Fix.** prepare-venue may rely ONLY on signals available BEFORE any candy is applied. Replace the agent poll with a pure-libvirt **domain-state preflight** (`ensureDomainBootable`): ONE `domain-state` RPC that hard-fails a terminal domain (`crashed` / `shut off` / `absent` / `unreachable`) in milliseconds — the early-abort value the gate was built for — then falls through to the ISO SSH bootstrap and the sshd wait, both available with no candy installed. Removed the now-dead `waitGuestAgent`, `probeGuestAgent`, `vmGuestAgentState`, `declaresGuestAgentChannel`, `guestAgentChannelName` (R5).

Concrete edits (2 files, +134/−189):

- `candy/plugin-deploy-vm/lifecycle.go` — the readiness sequence.
- `candy/plugin-deploy-vm/lifecycle_test.go` — new `ensureDomainBootable` tests + the package-wide guard.
