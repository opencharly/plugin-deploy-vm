# 2026.242.1719 — fix(prepare-venue): stop clobbering the ssh stanza vm create publishes

## Summary

A VM's managed ssh-config stanza had **two** writers, and on a rebuild the second one ran
last and clobbered the first.

`prepare-venue`'s own comment already states the intended design — `vm create` should be
*"the ONE writer of both the port allocation and the stanza"*. But its skip was gated on:

```go
deferToAutoBoot := vm.SSH != nil && vm.SSH.PortAuto && persistedPort == 0
```

That conflates two different questions:

| Question | Depends on `persistedPort == 0`? |
|---|---|
| who **allocates** the ssh port | yes — that is what the flag was for |
| who **writes** the stanza | **no** |

A port **is** persisted on every **rebuild**. So on a rebuild `deferToAutoBoot` is false,
`prepare-venue` runs *after* auto-boot's `vm create`, and replaces a correct stanza with one
carrying an unconditional `filepath.Join(stateDir, "known_hosts")`.

## Why that strands the guest

An installer-ISO guest changes its SSH host identity **exactly once**:

1. the live installer environment brings up its own sshd with freshly generated host keys —
   visible on Omarchy's own console as cloud-init generating keys for `root@archiso`,
2. the first thing to connect pins that key under `accept-new`,
3. the installer finishes and the guest reboots into the **installed** system, whose host keys
   are entirely different,
4. every connection after that fails with `Host key verification failed`.

Polling cannot recover from that, so the readiness gate burns its whole cap.

**Whether step 2 happens at all is a RACE** against the install finishing — which is why this
presented as intermittent. On one seed and one disk, the FIRST add of a domain took the
`deferToAutoBoot` branch and was correct; the rebuild of that same domain lost it.

    UserKnownHostsFile /home/atrawog/.local/share/charly/vm/charly-check-omarchy-iso-vm/known_hosts

**`vm create` was ruled out as that writer by direct A/B**, with two independently built
binaries, running the exact command the rebuild runs:

```
$ charly vm create omarchy-vm --domain check-omarchy-iso-vm
$ grep -A6 'Host charly-check-omarchy-iso-vm' ~/.config/charly/ssh_config | tail -1
    UserKnownHostsFile /dev/null
```

So the correct stanza is written, and then overwritten. That A/B is what turned a plausible
story into a located defect — the obvious suspect was innocent.

## The fix

The stanza write moves **after** the auto-boot block and is gated on whether `vm create`
actually ran:

```go
if shouldPublishStanza(deferToAutoBoot, createdByAutoBoot) { … }

func shouldPublishStanza(deferToAutoBoot, createdByAutoBoot bool) bool {
	return !deferToAutoBoot && !createdByAutoBoot
}
```

A named function rather than an inline `&&`, because the condition it replaces was wrong in a
way that was **invisible at the call site**: it *read* as "skip when auto-boot will write it"
and *meant* "skip when no port is persisted yet". Naming it puts the rule where a reader can
check it against the comment above it.

`vm create` stays the authority wherever it runs: it owns the per-domain state dir, the
allocated port, and the source-kind-dependent known-hosts policy.

That was my first and only intended fix, and it was **not sufficient** — see the next section.
There is a second path where prepare-venue is the legitimate sole writer, and on that path it
has to apply the policy itself.

`EnsureSshConfigInclude` becomes unconditional: the Include line is idempotent and must exist
on every path, including the one where `vm create` owns the stanza.


## The ordering fix alone was NOT enough — a live run said so

The first commit stopped prepare-venue overwriting the stanza *after* `vm create`. With only
that in place the bed was re-run, and the stanza was **still** clobbered — just earlier, at
`deploy-add` instead of at `update`:

```
19:02  UserKnownHostsFile /dev/null                       ← vm create (bed step)
19:03  UserKnownHostsFile .../charly-check-…/known_hosts  ← prepare-venue, during deploy-add
19:03  .../known_hosts written (99 bytes)                 ← the live-ISO key pinned
```

Why: `charly check run` runs `vm create` as its **own step** before `fleet add`. So by the
time prepare-venue runs, a port is persisted (`deferToAutoBoot` false) **and** the guest is
already reachable, so auto-boot does not run `vm create` (`createdByAutoBoot` false).
prepare-venue is then the *legitimate sole writer* — and it was inventing an unconditional
`filepath.Join(stateDir, "known_hosts")`.

So there are two distinct paths and **both** need handling:

| Path | Who writes | Fix |
|---|---|---|
| auto-boot ran `vm create` (rebuild) | `vm create` | prepare-venue must not overwrite — commit 1 |
| guest already reachable, no `vm create` | prepare-venue | it must apply the same policy — commit 2 |

Fixing only the first is what the second commit's live run disproved. That is why this PR has
two commits and not one.

### On the duplication, which is real

`plugin-vm`'s `publishVmSshAlias` applies the same `sourceKind == "iso"` rule. The
single-owner version — a shared `kit.VmKnownHostsFile` — **was implemented**
(`opencharly/sdk#199`) and correctly **blocked as a partial cutover**: a shared function
lands with zero callers, and consumers can only adopt it once it is tagged, so no single PR
can both add it and use it. That PR is closed with that reason, not left open.

Given the choice between leaving a measured, guest-stranding bug open behind a three-repo
repin chain, and expressing a one-line rule in the second writer with a test that names the
first, this PR takes the second. `TestKnownHostsPathFor` names
`candy/plugin-vm/vm_create_orchestrate.go` explicitly so the pair is findable from either
side. That is a trade, and it is stated rather than hidden.

## How tested

```

ok  	github.com/opencharly/plugin-deploy-vm/candy/plugin-deploy-vm	0.004s
?   	github.com/opencharly/plugin-deploy-vm/candy/plugin-deploy-vm/cmd/serve	[no test files]
```

Complete output, `-count=1`, nothing elided.

`TestShouldPublishStanza` covers the four reachable input combinations, including the two the
old condition got right (so the fix is not a blanket "never write"):

- fresh domain → skip (vm create owns port and stanza)
- **rebuild, vm create ran → skip** ← the regression
- port persisted, guest already reachable, no create → write
- auto-boot disabled → write

**Negative control — restore the original condition** (`return !deferToAutoBoot`):

```
--- FAIL: TestShouldPublishStanza
    REBUILD — port persisted, and auto-boot ran vm create: got true, want false —
    THE REGRESSION: vm create just published the correct stanza; writing now replaces
    its source-kind-dependent known-hosts policy and strands the guest
--- FAIL: TestPrepareVenueNeverWritesAfterVmCreate
    deferToAutoBoot=false: prepare-venue would write the stanza AFTER `vm create`
    published it, discarding the known-hosts policy only vm create knows
    (an iso guest must record no host key). That is the measured defect.
```

`TestPrepareVenueNeverWritesAfterVmCreate` is written as an **invariant over every other
input** rather than a case, because that is the single property the defect violated and the
one a future edit is most likely to lose. Its complement
(`TestPrepareVenueWritesWhenNothingElseWill`) exists so the fix cannot degrade into never
writing, which would leave `ssh <alias>` unresolvable.

## Rulebook compliance

- **R1 — RCA every anomaly.** Root-caused from a measured failure to the exact line, and the
  obvious suspect (`vm create`) was **eliminated by A/B with two independently built
  binaries** before any code was written. The intermittency was explained — a race whose
  outcome flips between the first add and the rebuild — not tolerated as flake.
- **R2 — Finish the whole cutover.** One repo, one commit, both the fix and its guard. An
  earlier attempt at this same bug put a shared policy function in `sdk` with no callers; the
  validator correctly blocked it as a partial cutover (opencharly/sdk#199, closed with the
  reason). This version needs no repin chain.
- **R3 — No duplication.** The rejected alternative was copying the `if sourceKind == "iso"`
  guard into this file. That is one rule in two places, which is precisely how the two writers
  came to disagree. There is now one writer.
- **R4 — No workarounds.** Not a longer readiness cap, not a retry, not a bed weakened to
  pass. A longer cap was the tempting fix and cannot work: the condition never becomes true.
- **R4a — Fix the product first.** The documented-caveat version ("clear `known_hosts` by hand
  between rebuilds") would have made a race-conditioned failure look intended.
- **R5 — Delete legacy completely.** The old unconditional write is deleted, not left behind a
  flag.
- **R6 — Git safety.** `git status` inspected before the commit; branched from a fresh
  `origin/main`; no force-push, no hook bypass, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** A negative control that restores the original
  condition and reproduces the exact defect, plus the complementary invariant.
- **R8 — Preserve emitted artifacts.** The emitted artifact is the ssh_config stanza. The
  defect was precisely that it was emitted correctly and then destroyed; this change stops
  the destruction.
- **R9 — Binary equals source.** N/A — plugin-deploy-vm is a candy; no dependency change and
  no new runtime OS dependency.
- **R10 — Fresh disposable proof.** Met. `check-omarchy-iso-vm` is `disposable: true` and goes
  from `FAIL (steps=6)` — reproduced twice at the released plugin — to `PASS (steps=9)` with
  this PR and nothing else changed, including `[check-live-rebuild] 13/13` against the guest
  the disposable rebuild installed from a blank disk.
