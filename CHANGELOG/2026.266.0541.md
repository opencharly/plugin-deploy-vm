# 2026.266.0541 — fix: re-pin sdk so the in-plugin project load honors the config-stack overlay fix

## Summary of changes

Bump `github.com/opencharly/sdk` `v0.2026253.1947` → `v0.2026265.2104` (and the `github.com/opencharly/spec` require it carries) so this plugin's OWN project self-load stops raw-merging the per-host deploy overlay as a config-stack PROJECT layer.

**WHY.** This plugin is an out-of-process `deploy:vm` substrate: it **self-loads the project** (`loaderkit.LoadUnifiedViaExecutor`, `lifecycle.go`) to resolve the VM entity for `PrepareVenue`. Under the old pin, that load used the **pre-fix** config stack, which raw-merged `~/.config/charly/charly.yml` (a `DeployConfig` — per-host RUNTIME state) as a project document layer. For a member-bearing bed this injects a deploy-level member's TOP-LEVEL persisted copy next to the member its owner still declares nested, and `FoldMembers` rejects it:

```
peer name "preempt-vm-taker" (declared under deploy "check-preempt-vm-live")
collides with an existing deploy/bed/peer entry — peer names must be globally unique
```

Observed live on `check-preempt-vm-live` (in its `distro-fedora` origin AND its relocated `plugin-preempt` copy), failing at `bring-up-members` (`steps=9`).

**Why a separate re-pin here.** `opencharly/sdk#270` fixed the sdk; `opencharly/charly#631` re-pinned charly core + the compiled-in plugins. An **out-of-process plugin vendors its OWN `loaderkit`** (its own `go.mod` sdk require + its own compiled binary), so it does not inherit the core pin — each self-loading plugin must re-pin in its own repo. This is that re-pin for `plugin-deploy-vm`.

**Concrete edits:**
- `candy/plugin-deploy-vm/go.mod` — sdk `v0.2026253.1947` → `v0.2026265.2104`; spec → `v0.2026262.957` (the sdk's own require).
- `candy/plugin-deploy-vm/go.sum` — the corresponding checksums (plus the transitive `golang.org/x/*` bumps the newer sdk/spec require).
